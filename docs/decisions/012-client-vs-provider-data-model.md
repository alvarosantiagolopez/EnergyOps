# ADR 012: Model client and energy provider as separate entities

## Status
Accepted

## Context
Every feature built so far (historical comparison, anomaly detection, CRM contacts, the prioritization agent, Priority Queue) grouped and compared invoices by `company` — the field `claudeService.extractInvoiceData()` extracts from the PDF itself, i.e. the **energy provider issuing the bill** (Endesa, Iberdrola, Naturgy, ...). `crmService.syncInvoiceToCRM()` found-or-created `crm_contacts` rows keyed on that same provider name, and `analysisService.analyzeInvoice()` pulled historical invoices with `WHERE company = $1`.

This is a data modeling bug once framed against the company's actual business: The company doesn't manage energy for Endesa — Endesa is who bills company's actual client (a business or real estate group). The **client** is the entity company has a relationship with and needs to track over time; the **provider** is metadata about a single invoice, not an identity to group by. Two consequences of conflating them:

- **False grouping**: if a client switches providers (or a real estate group has multiple properties each on a different provider), their invoices would be split across unrelated "companies" in every historical comparison, CRM contact, and Priority Queue row — even though it's the same client.
- **False collision**: worse, if two *different* clients both happen to use Endesa (extremely common — Endesa is a national utility with a huge, unrelated customer base), the app would silently merge their invoices into one `crm_contacts` row and one historical baseline. `analyzeInvoice()` would compare Client A's January invoice against Client B's consumption average, and the prioritization agent would reason over a "historical pattern" that blends two unrelated businesses. In production this isn't a cosmetic issue — it produces meaningless anomaly detection and a prioritization decision an account team could not trust.

## Decision
- **`invoices.client_name`** (new column) is the primary grouping key for everything that was previously grouped by `company`: `analysisService.analyzeInvoice()`'s historical comparison query, and the `historicalInvoices` lookup in `POST /api/invoices/extract` and `backend/db/seed.js`. `company` remains on the row, now understood purely as invoice metadata (which provider issued this specific bill).
- **Client name is supplied by the user at upload time**, not extracted from the PDF — the invoice document has no notion of "who company's client is," only who issued it. `UploadView.jsx` adds a required "Client name" text input (with a `<datalist>` populated from `GET /api/invoices/client-names`, a new endpoint backed by `analysisService.fetchDistinctClientNames()`) alongside the file dropzone. The value is sent as a `clientName` form field alongside the file in `POST /api/invoices/extract` and threaded through `extractedData.clientName` for the rest of the pipeline (analysis, save, CRM sync, agent prompt, email alerts).
- **`crm_contacts` is now keyed by client name**, not provider. The existing `company_name` column is reinterpreted to hold the client name (find-or-create in `crmService.syncInvoiceToCRM()` now matches on client identity); a new `provider` column stores the *last known* energy provider for that client, so the UI can still show "via Endesa" as a secondary detail without conflating it with the grouping key.
- **Frontend displays client name as the primary identifier everywhere**, with provider shown as a secondary detail ("Mercadona - Gran Vía 12 · via Endesa"): Result view's Company metric card, Priority Queue's Client column, History's Client column, and Dashboard's latest-anomaly banner.
- **Seed data** (`backend/db/seed.js`) assigns each of the 9 seeded invoices to one of three fake clients — "Mercadona - Gran Vía 12" (6 Endesa invoices), "Grupo Inmobiliario Aurora" (2 Iberdrola invoices), "Hostelería Sur S.L." (1 Naturgy invoice) — keeping the existing providers as invoice metadata. The seed script's historical-lookup query and its final console summary were updated to reflect client-scoped grouping.

## Rationale
- **Why not just rename `company` to mean "client" and drop provider entirely**: the provider is real, useful invoice metadata (which utility issued this bill, at what rate) that the extraction pipeline already gets for free from the PDF — throwing it away loses information the UI already surfaced as "Company" throughout. Keeping both, with clearly separated meanings, costs one extra column and is strictly more correct.
- **Why the client name is a manual input instead of something inferred/extracted**: the invoice PDF is issued by the provider *to* the client, but nothing on a residential/small-business energy bill identifies "the real estate group or portfolio the company is managing this property for" — that's business context that exists in company´s own records, not on the document. A required text field (with autocomplete over previously used names) is the simplest honest model of "the user tells us who this is for," and mirrors how a real the company ops person would pick an existing client from a CRM rather than re-type it.
- **Why `crm_contacts.company_name` is reinterpreted rather than renamed**: renaming the column would touch every existing query (`getAllContacts`, `saveAgentDecision`, the Priority Queue frontend's `contact.company_name` reads) for a purely cosmetic gain, since the column has always just been "the string we group contacts by" — swapping what string it holds (client instead of provider) is the substantive fix, not the column's literal name.

## Trade-offs accepted
- `crm_contacts.company_name` is now semantically "client name" while still named `company_name` in the schema — mildly confusing to a future reader who doesn't check this ADR. Acceptable given the alternative (renaming) touches significantly more code for no functional benefit.
- If two different real users happen to type slightly different spellings of the same client name (e.g. "Mercadona" vs. "Mercadona - Gran Vía 12"), they'll be tracked as separate clients. This is inherent to free-text identity matching and is why the datalist autocomplete exists — it nudges toward reusing an exact prior name without hard-enforcing it via a separate `clients` table, which would be over-engineering for a portfolio project's single-user demo flow.

## Consequences
- `backend/db/schema.sql`: `invoices.client_name VARCHAR(255)` added; `crm_contacts.provider VARCHAR(255)` added.
- `backend/routes/invoices.js`: `POST /api/invoices/extract` now requires a `clientName` form field (400 if missing/blank) and exposes a new `GET /api/invoices/client-names` endpoint.
- `backend/services/analysisService.js`: `analyzeInvoice()` takes a `clientName` param and filters history by it; `saveInvoice()` persists `client_name`; new `fetchDistinctClientNames()`.
- `backend/services/crmService.js`: `syncInvoiceToCRM()` finds-or-creates by client name and stores `provider` separately.
- `backend/services/agentService.js` / `emailService.js`: prompts and alert emails now reference both client and provider, with client as the primary identity.
- `backend/db/seed.js`: each seed entry has a `client_name`; historical lookup and console summary are client-scoped.
- Frontend: `UploadView.jsx` (client name input + datalist), `ResultView.jsx`, `PriorityQueueView.jsx`, `HistoryView.jsx`, `DashboardView.jsx` all show client name as primary with provider as secondary detail; `api.js` gains `fetchClientNames()` and `extractInvoice()` now takes a `clientName` argument.
